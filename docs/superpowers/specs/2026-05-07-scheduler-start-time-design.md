# 群组定时开始时间设计

## 背景

当前群组摘要调度只按 `summaryInterval` 和 `lastSummaryAt` 计算。对于 24 小时间隔的群组，只能从首次摘要或上次摘要完成时间开始滚动，无法稳定在“每天早上 8 点”这类固定本地时间生成早报。

目标是保留现有按间隔运行能力，同时允许群组配置一个开始时间，并通过后端环境变量配置时区，避免将上海时间写死在代码中。

## 目标

- 群组可选配置 `summaryStartTime`，格式为 `HH:mm`。
- 后端新增全局 `SCHEDULER_TIMEZONE`，默认 `Asia/Shanghai`。
- 当群组设置 `summaryStartTime=08:00` 且 `summaryInterval=24` 时，每天按配置时区的 08:00 生成摘要。
- 当间隔为 6 小时时，从开始时间开始按 6 小时递增，例如 `08:00、14:00、20:00、02:00`。
- 新建群组后立即运行一次摘要任务，随后进入锚点调度。
- 项目重启时保留立即检查，但只在确实错过调度锚点时补跑，避免因为重启重复生成。

## 非目标

- 不引入 cron 表达式。
- 不支持每个群组单独配置时区。
- 不改变手动“生成总结”的入口语义。
- 不重构 AI 摘要生成流程或 Telegram 消息拉取流程。

## 数据模型

在 `groups` 表新增字段：

- `summary_start_time text nullable`

含义：

- `null`：使用旧的滚动间隔逻辑。
- `HH:mm`：使用配置时区内的日内开始时间作为调度锚点。

共享校验 schema 新增：

- `summaryStartTime: z.string().regex(/^([01]\d|2[0-3]):[0-5]\d$/).nullable().optional()`

前端类型来自数据库模型推导，不需要单独维护字段类型。

## 配置

后端环境变量新增：

- `SCHEDULER_TIMEZONE=Asia/Shanghai`

校验策略：

- 在 `env.ts` 中默认 `Asia/Shanghai`。
- 调度服务启动时用 `Intl.DateTimeFormat` 尝试构造 formatter，若时区非法则启动失败并给出清晰错误。

`.env.example` 中加入调度配置段，说明该值使用 IANA timezone 名称。

## 调度语义

### 未配置开始时间

保持当前逻辑：

- `lastSummaryAt` 为空：需要生成。
- `now - lastSummaryAt >= summaryInterval`：需要生成。
- 摘要窗口为 `lastSummaryAt ~ now`，首次为 `now - interval ~ now`。

### 配置开始时间

使用 `summaryStartTime + SCHEDULER_TIMEZONE` 生成一组时间锚点。

每次检查时：

1. 将当前 UTC 时间转换为配置时区下的本地日期时间。
2. 找到当前时间之前或等于当前时间的最近一个调度锚点 `dueAt`。
3. 若 `lastSummaryAt` 为空，或者 `lastSummaryAt < dueAt`，则创建摘要任务。
4. 摘要窗口为 `dueAt - summaryInterval ~ dueAt`。
5. 创建任务后立即将群组 `lastSummaryAt` 更新为 `dueAt`，防止下一分钟重复创建同一个锚点任务。

示例：

- 时区：`Asia/Shanghai`
- 开始时间：`08:00`
- 间隔：`24`
- 当前时间：`2026-05-07 08:01`
- `dueAt`：`2026-05-07 08:00`
- 窗口：`2026-05-06 08:00 ~ 2026-05-07 08:00`

如果服务在 `2026-05-07 09:00` 重启且当天 08:00 尚未跑过，会补跑一次 08:00 的窗口。若当天 08:00 已跑过，不会重复创建。

## 新建群组立即运行

创建群组成功后，后端立即创建并异步执行一个 `scheduled` 任务：

- `periodEnd = now`
- `periodStart = now - summaryInterval`

该任务执行后会更新 `lastSummaryAt`。如果群组配置了开始时间，后续调度仍按下一个锚点运行；如果最近锚点已经被 `lastSummaryAt` 覆盖，重启检查也不会重复生成。

如果立即任务创建或执行失败：

- 创建群组接口仍返回成功，因为群组已经创建。
- 日志记录错误，用户可在任务列表看到失败任务，或等待下一次调度。

## 重启行为

调度器启动时继续立即调用一次检查，以支持服务停机期间错过的锚点补跑。

区别是配置开始时间后，判断依据从“当前实际时间是否超过间隔”变成“最近锚点是否已经被覆盖”。这能避免服务在锚点之后频繁重启时重复创建摘要。

## 前端

群组配置表单新增“开始时间”字段：

- 编辑态：`<input type="time">`
- 展示态：未设置显示“按间隔滚动”，已设置显示配置值。

父群组和 topic 配置都支持该字段。保存时随现有 PATCH 请求一起提交。

## API

`PATCH /api/groups/:id` 支持：

- `summaryStartTime?: string | null`

`POST /api/groups` 暂不要求传入开始时间，群组新建后用户可在配置中设置。

## 测试

重点覆盖：

- `summaryStartTime` 校验接受 `00:00、08:00、23:59`，拒绝非法时间。
- 24 小时间隔在 `Asia/Shanghai` 的 `08:00` 只生成一次当天锚点任务。
- 6 小时间隔从 `08:00` 推导出正确锚点。
- 重启后如果错过锚点则补跑，如果 `lastSummaryAt >= dueAt` 则不重复跑。
- 未配置 `summaryStartTime` 的群组保持旧行为。
- 新建群组后立即创建一次任务。

## 风险与处理

- JavaScript 原生时间 API 对 IANA 时区计算不够直接。实现时应把时区换算逻辑封装成小工具函数，并为它添加单元测试。
- `lastSummaryAt` 过去表示实际触发时间；配置开始时间后，定时任务会把它作为“已覆盖窗口结束时间”。手动任务仍可由摘要生成流程更新为实际完成附近时间，后续定时判断只关心它是否覆盖最近锚点。
- 如果服务停机跨过多个锚点，本设计只补跑最近一个锚点，避免一次重启堆积大量历史任务。
